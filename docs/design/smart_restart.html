GenPipes · design proposal

Smart restart

For team review GenPipes 7.0 · breaking changes allowed SLURM · PBS · batch
  • Problem 1: jobs that fail for memory or walltime need a manual fix and resubmission.
  • Problem 2: changing threads/ram reruns finished jobs and everything downstream.
  • Fix: resource values become runtime variables, so they're no longer in the job hash. Failed jobs get more resources when genpipes is rerun, and an opt-in Slurm monitor retries them automatically.
  • Key decisions: hashes break once in 7.0, with a migration tool; an explicit resource API; JOB_LIST is the source of truth; PBS gets everything except the monitor; the safety net comes first.

Cause

  • The .done name is md5(command_with_modules). cluster_* values aren't hashed, but the inis copy them into commands: threads = %(cluster_cpu)s, ram = %(cluster_mem)s (which becomes -Xmx), options = -t %(cluster_cpu)s.
  • So a resource change changes the hash, the job reruns, and is_up2date cascades to every child job.
  • A Java heap error can't be fixed through cluster_mem alone: -Xmx is written into the command, and the job ends as FAILED.

A · Explicit resources

ram   = global_conf.resource(section, "ram")        # "${GP_RES_<section>__ram}", plain str
ram_g = global_conf.resource_value(section, "ram")  # "16G", only for Python logic
command = f"java -Xmx{ram} -jar picard.jar MarkDuplicates ..."
  • The variable is plain text, so every way of building a string gives the same result. A str/int subclass doesn't work: join, + and %d use the real value. All ~300 call sites are converted.
  • tmp_dir is never hashed. java_other_options stays hashed, except the JVM resource flags inside it (-Xmx, -Xms, GC thread counts).
  • ini cleanup: options = -t %(cluster_cpu)s becomes a threads key. --sanity-check reports an error when an option copies in a resource value.
  • Values are exported at submission through the heredoc path. The .sh keeps defaults so it can be run by hand.
  • hash_resources = threads keeps thread counts in the hash for tools whose output depends on them. .done becomes JSON.
  • Migration: genpipes tools migrate_done <dir> [--dry-run] [--keep-legacy] renames 6.x .done files to their 7.0 names. Going back to 6.x needs --keep-legacy.

B · Attempt history

job_id  job_name  dependencies  output  attempt  replaces_id  failure_class  resources
  • Each restart appends a row; the last row for a job name is its current attempt. Readers use column names.
  • Failure classes come from a pure, tested core/failure.py: sacct states on SLURM, Torque messages on PBS, exit 137 in batch, plus log patterns such as java.lang.OutOfMemoryError. The classes are MEMORY/TIME (escalate), NODE (rerun as is) and OTHER (never retried).

C · Escalation at regeneration

bwa_mem2.S1 failed OUT_OF_MEMORY (attempt 2/3): cluster_mem 32G -> 48G, ram 30G -> 45G
  • Only the failed job's resources change; its hash doesn't, so other samples aren't affected. Flags: --no-escalate, --reset-attempts.
  • Duplicate guard: jobs whose latest attempt is still pending or running are skipped (--force overrides).
[DEFAULT]
retry_max_attempts    = 3          # including the first; 1 disables
retry_on              = MEMORY,TIME,NODE
retry_mem_factor      = 1.5        # also scales ram/-Xmx
retry_walltime_factor = 2
retry_cpu_factor      = 1
retry_fail_patterns   = java.lang.OutOfMemoryError,std::bad_alloc,Cannot allocate memory

D · Restart monitor (Slurm, --monitor)

A pure reconcile(dag, states, history, policy) → actions, plus a Slurm adapter with four operations: query, submit, update dependencies, cancel.

flowchart TD
  A["Wake up (every 10 min)"] --> B["Read JOB_LIST"]
  B --> C["One sacct call for all jobs"]
  C --> D{"Any job failed?"}
  D -- yes --> E["Handle each failed job"]
  D -- no --> F{"All jobs finished?"}
  E --> F
  F -- no --> A
  F -- yes --> G["Summary, stop"]

flowchart TD
  A["A job failed"] --> B{"Why?"}
  B -- "memory / time / node" --> C{"Retries left,
under caps?"}
  B -- "other error" --> X["Give up: cancel waiting jobs, report"]
  C -- no --> X
  C -- yes --> R["Resubmit with more resources (new id)"]
  R --> W["Waiting jobs now wait on the new id"]

Example: markdup.S1 (job 1003) runs out of memory at 16G. At the next check the monitor resubmits it with 24G as job 1005, appends a JOB_LIST row (attempt 2, replaces 1003) and points call.S1 at 1005.

  • Lock: one per JOB_LIST, created atomically and kept alive with a heartbeat. No flock, which is unreliable on Lustre.
  • No double submission: the row is written right after sbatch, and --comment=gp:<job>:<attempt> lets a restarted monitor find attempts it already submitted.
  • Waiting jobs: with --monitor, jobs that have dependencies get --kill-on-invalid-dep=no. Every checked cluster sets kill_invalid_depend, which would otherwise cancel them as soon as their parent fails. Pending ones are reconnected with scontrol update, cancelled ones are resubmitted, and on a final failure they're cancelled (plus monitor --cleanup).
  • Late submissions: a job submitted later with an old id is fixed at the next check.
  • Limits: at most 5 scheduler calls per second, and a check that there's room under the 1000-job limit.
  • Files per attempt: a new restart_N.submit and restart_N.o; the scientific .sh is reused.
  • Hosting: one 1-CPU, about 1 GB, 24 h job that resubmits itself until the pipeline is done (scrontab is disabled, login nodes are off-limits). Cost: about 24 core-hours per day per pipeline.
  • Polling: one sacct per check, every 10 min, growing to 30 min when idle. Nextflow's Alliance config polls every 60 s.

PBS (Abacus)

PBS gets parts A, B, C and the duplicate guard, but not the monitor. That would need a PBS adapter, a way to host the monitor and Abacus IT's involvement, all thrown away after a move to Slurm. --monitor on PBS stops with a clear message.

Features that need Slurm: the case for migrating Abacus

  1. Automatic retries. On Abacus, the user still has to rerun genpipes.
  2. Reliable failure detection: Slurm job states, versus parsing PBS logs.
  3. Accurate usage data. The PBS epilogue estimates requested memory from the CPU count (×5G, or ×15G on lm) and records no average memory or disk I/O, so right-sizing is unreliable.
  4. Epilogue changes without IT. #PBS -T GenPipes needs Abacus IT to redeploy every change.
  5. Dependency control: keeping waiting jobs pending and reconnecting them to a new job.
  6. One code path instead of two to maintain and test.
