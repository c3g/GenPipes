GenPipes · design proposal · revision 2

Smarter restart

Retry jobs that fail for lack of memory or walltime automatically, with more resources each time, and stop resource changes from rerunning work that is already done.

Proposal · for team review SLURM · PBS · batch Not implemented

Revision 2: automatic retries now run through an external monitor that reconciles the job DAG, following a team member's proposal. The in-job retry from revision 1 is now under alternatives considered.

The two problems

  1. Resource failures need manual work. When a job fails with OUT_OF_MEMORY, TIMEOUT or a Java heap error, the user reads the log, edits an ini, runs genpipes again and resubmits. Nothing retries automatically.
  2. Changing a resource restarts finished work. Raising threads or ram for one failed sample reruns every done job in that step, and everything downstream of it.

Root cause

The done file is named after md5(job.command_with_modules). The cluster_* values are not in that hash; they only go into #SBATCH lines. But the base inis copy resources into the command, so they end up hashed anyway.

TODAY · values are part of the hash 
[picard_mark_duplicates]
cluster_mem = 16G
ram = %(cluster_mem)s

# scientific .sh (hashed)
java -Xmx16G -jar picard.jar \
  MarkDuplicates ...
PROPOSED · only the variable name is hashed 
# submission file (not hashed)
export GP_RES_picard_mark_duplicates__ram=16G

# scientific .sh (hashed)
java -Xmx${GP_RES_picard_mark_duplicates__ram} \
  -jar picard.jar MarkDuplicates ...

Across bfx/ there are about 93 threads, 154 ram, 94 java_other_options and 165 tmp_dir lookups, plus free-form values such as options = -t %(cluster_cpu)s. Job.is_up2date returns False as soon as any upstream job is scheduled, so one changed hash cascades to every child job.

A retry, whether started by a monitor or by a user, can't change memory or threads without changing the scientific .sh. With today's hashing, that also moves the job's .done path. So resource values must become runtime variables before automatic retries can work.

Design in four parts

AResource tokens

Resource values in commands become ${GP_RES_…} variables. The hash sees only the name.

all schedulers
BAttempt history in JOB_LIST

Each submission row records attempt, replaced id, failure class and resources. The last row for a job name is its current attempt.

all schedulers
CEscalation at regeneration

Running genpipes again raises resources only for jobs that failed for a resource reason.

all schedulers
DRestart monitor

Checks the jobs regularly, resubmits resource failures with more resources and reconnects their descendants.

SLURM · then PBS · batch loop

A · Resource tokens

  • The ini lists which keys are resources, by class: CPU (cluster_cpu, threads, *_threads), memory (cluster_mem, ram, *_ram, max_records_in_ram), time (cluster_walltime), and opaque (tmp_dir: kept out of the hash, never scaled).
  • java_other_options stays hashed. Its content depends on the tool behind it, so only the known JVM resource flags inside it (-Xmx, -Xms, -XX:ParallelGCThreads, -XX:ConcGCThreads, -XX:ActiveProcessorCount) become tokens. Everything else stays in the hash. In the worst case, a change that only affects speed still reruns the job, which is today's behaviour.
  • global_get returns a ResourceInt/ResourceStr. It keeps the real value for Python logic and renders as a token in commands. Arithmetic falls back to a literal value, which behaves exactly as it does today.
  • A custom configparser.Interpolation turns %(cluster_cpu)s inside free-form options into tokens, so the inis don't need edits.
  • Job collects its tokens into job.resources. The scheduler reads resources from there, which is what makes per-job escalation possible.
  • Values are exported in the submission file. The scientific .sh carries : "${VAR:=default}" lines, so it can still be run by hand.
  • Per-step opt-out hash_resources = threads puts values back in the hash for tools whose output depends on the thread count.
  • Migration: if the new .done is missing but the legacy-hash .done exists, accept it and create the new one. Upgrading mid-project then reruns nothing.
  • .done gets JSON content (hash, resources, attempt, job id, version). Up-to-date checks still only test that it exists.

B · Attempt history in JOB_LIST

JOB_LIST already has one row per submitted job (id, name, dependency ids, .o path), which is enough to rebuild the DAG. It becomes the source of truth. There is no SQLite: its locking is unreliable on Lustre/NFS. New columns are appended, and existing readers use columns 0–3 by position:

id  name  deps  o_path  attempt  replaces_id  failure_class  resources_json
  • Each restart appends a row, so the last row for a job name is its current attempt. cancel_running_pipeline then also cancels the retries.
  • One classifier, core/failure.py:
    • SLURM: the sacct state.
    • PBS: the scheduler's "exceeded limit" messages plus the exit code.
    • Batch: exit code 137.
    • All schedulers: retry_fail_patterns in the .o, such as java.lang.OutOfMemoryError.
  • Classes: MEMORY and TIME (escalate), NODE (rerun as is), OTHER (never retried).

C · Escalation at regeneration

create_jobs reads every job_list.* file in job_output/. When a job is not up to date and its last attempt failed with MEMORY or TIME, only that job's resources are scaled, and the change is logged:

bwa_mem2.S1 failed OUT_OF_MEMORY (attempt 2/3): cluster_mem 32G -> 48G, ram 30G -> 45G

Thanks to A, samples S2 to Sn keep their hashes. New flags: --no-escalate and --reset-attempts. C and the monitor use the same policy, per step with [DEFAULT] as fallback, and the caps come from the cluster inis:

[DEFAULT]
retry_max_attempts    = 3          # including the first; 1 disables retries
retry_on              = MEMORY,TIME,NODE
retry_mem_factor      = 1.5        # cluster_mem and every mem-class token
retry_walltime_factor = 2
retry_cpu_factor      = 1
retry_fail_patterns   = java.lang.OutOfMemoryError,std::bad_alloc,Cannot allocate memory
monitor_interval      = 10m        # grows to monitor_max_interval when nothing changes
monitor_max_interval  = 30m
retry_max_mem         = 750G       # caps set per cluster in common_ini/*.ini
retry_max_walltime    = 7-00:00:00
retry_max_cpu         = 192

D · Restart monitor

genpipes tools monitor <job_list> does two things.

1. A check every 10 minutes (monitor_interval):

flowchart TD
  A["Wake up (every 10 min)"] --> B["Read JOB_LIST:
which jobs exist and which depends on which"]
  B --> C["Ask SLURM the state of every job
(one sacct call)"]
  C --> D{"Did any job fail?"}
  D -- yes --> E["Handle each failed job
(next chart)"]
  D -- no --> F{"Are all jobs finished?"}
  E --> F
  F -- "no: sleep 10 min" --> A
  F -- yes --> G["Print a summary and stop"]

2. The decision for each failed job:

flowchart TD
  A["A job failed"] --> B{"Why?
(SLURM state + its log)"}
  B -- "out of memory or out of time" --> C{"Retries left and
under the cluster limits?"}
  B -- "node crashed" --> C
  B -- "any other error
(bug, bad input)" --> X["Give up on this job:
cancel the jobs waiting on it
and report it"]
  C -- no --> X
  C -- yes --> R["Resubmit it with more memory or time
(it gets a new job id)"]
  R --> W["Jobs waiting on the old id
now wait on the new id"]

Example. The chain is trim.S1 → align.S1 → markdup.S1 → call.S1, and markdup.S1 (job 1003) runs out of memory at 16G.

CheckWhat SLURM reportsWhat the monitor does
10:001003 OUT_OF_MEMORY; call.S1 waiting on 1003Resubmits markdup.S1 with 24G as job 1005 and adds a JOB_LIST row (attempt 2, replaces 1003). Changes call.S1 to wait on 1005.
10:101005 running, call.S1 waitingNothing failed, so it sleeps.
LaterAll jobs completedPrints a summary and stops.

The details of each part:

  1. Lock. job_output/.monitor.lock holds host, pid and a heartbeat time. Another monitor can take over only when the heartbeat is older than 3 cycles. Don't rely on flock on Lustre.
  2. DAG. Rebuilt from JOB_LIST (plus chunk_N.out for chunked submissions), taking the latest row per job name.
  3. One scheduler query per cycle: sacct -X -P -j <ids> on SLURM, qstat -f -x on PBS.
  4. Retry. Write restart_N.submit with scaled resources and reuse the scientific .sh. Run sbatch with no dependency: the job ran, so its parents had completed. Append its JOB_LIST row right away, so a crash mid-cycle can't submit the job twice. --comment=gp:<job>:<attempt> lets a restarted monitor find attempts it submitted but never recorded.
  5. Reconnect descendants, in DAG order. A running job never needs reconnecting: its afterok dependencies were met before it started. Pending descendants get scontrol update Dependency= with the current ids, which keeps their queue priority. Descendants that were already cancelled are resubmitted.
  6. Keep children pending. Rorqual, fir and narval all set kill_invalid_depend, so by default Slurm cancels the children of a failed job immediately. With --monitor, jobs that have dependencies are submitted with --kill-on-invalid-dep=no, which overrides the cluster setting for that job (confirmed in the sbatch man page on all three). They stay pending until the monitor reconnects them. If the monitor stops for good, the final-failure path, a log_report warning and monitor --cleanup make sure they don't stay pending for ever.
  7. Throttle and respect limits. Rorqual limits each user to bursts of 50 scheduler requests, then about 10 per second. The monitor spaces its sbatch and scontrol calls (at most 5 per second). It also checks that there is room under the 1000-job submit limit before resubmitting, and waits for the next check if there isn't.
  8. Late submissions. A pending job still pointing at a replaced id is fixed in the same pass. That covers children submitted after the retry by chunk_and_submit_genpipes. Running a cycle twice does no harm.
  9. Final failure: cancel the pending descendants and record the reason. The monitor stops when every job's latest row is completed or a final failure.

Where the monitor runs

Alliance does not allow long-running processes on login nodes. sbatch works from inside jobs (confirmed by the team).

  1. One long, small monitor job (preferred). 1 CPU, about 1 GB, 24 h. It runs the check loop itself. Shortly before its walltime, if the pipeline isn't finished, it submits its replacement and exits. Narval asks for jobs of at least one hour and at most 1000 jobs per user (from a search snippet of the Narval wiki page). A 5-minute job resubmitted every 10 minutes would conflict with that, and each run would also wait in the queue. Cost: about 24 core-hours per day per pipeline. Later refinement: one monitor per user watching all their active pipelines.
  2. scrontab, Slurm's own scheduler-side cron. Not available on rorqual, fir or narval: "scrontab is disabled on this cluster". Kept only as an option for other sites.
  3. In the foreground, for a local run or a user's own server.

Batch mode has no monitor; each job is wrapped in a memory-retry loop instead.

Polling frequency

  • One state query per check: a single sacct -X -P -j <ids> for every current id. sacct reads Slurm's accounting database, not the main scheduler process (slurmctld), which is the one that slows down for everyone when it's flooded.
  • squeue and scontrol only when a job failed, to reconnect its pending descendants.
  • Adaptive: 10 min by default, growing to 30 min after 3 checks in a row with no change, and back to 10 min after any change. Values below 2 min are refused.
  • For comparison, the nf-core configuration for Alliance clusters has Nextflow poll every 60 s. This design is 10–30 times lighter, and a few minutes of delay is short compared with how long a job runs before it hits a limit.

How the parts work together

  • The user does nothing. The monitor retries resource failures while the pipeline runs.
  • The monitor gives up or isn't used. The user runs genpipes again, and escalation at regeneration starts from the JOB_LIST history.
  • The user edits resources by hand. Thanks to the resource variables, done jobs and their descendants are not rerun.

Alternatives considered

OptionWhy not chosen
In-job retry from the EXIT trap (rev. 1)Can't run when the job is SIGKILLed at walltime or killed outright by PBS at its memory limit. Needs sbatch from every job. Children submitted after the retry still point at the old id. The logic would be split between bash and Python.
SQLite for the DAGJOB_LIST already has the DAG, and SQLite locking is unreliable on Lustre/NFS.
Appending restarts to the .shRunning the script again would resubmit them.
Login-node daemonNot allowed by Alliance policy. Replaced by a monitor job.
Short monitor job every 10 minConflicts with Narval's one-hour minimum, and each run waits in the queue, so checks would be irregular. Replaced by one long monitor job.
Requeue the same job idUsers cannot increase a pending job's TimeLimit, so TIMEOUT can't be fixed. Requeue is also disabled on rorqual, fir and narval (JobRequeue = 0).
Sentinel job per jobDoubles the job count, and cluster_max_jobs is 3000 on rorqual.
Search-and-replace hashingFragile: a value like 8 can appear anywhere in a command.
Explicit API at each call siteMeans editing about 300 call sites. Tokens give the same result through the config layer.

Testing

  • Unit tests (new): the hash is stable when threads, ram or tmp_dir change and changes when a scientific option changes; opt-out; legacy migration; escalation math (units, per cpu, caps); classifier on recorded sacct, PBS and Java logs.
  • Monitor with a fake scheduler: uses recorded JOB_LIST and sacct output. Checks which jobs are retried, reconnected, resubmitted or cancelled; DAG order; a crash mid-cycle followed by a restart, with no double submission; a late child pointing at a replaced id; and two monitors started at once.
  • Script snapshots: generate the rnaseq_light, dnaseq and chipseq scripts before and after. The only differences should be tokens and exports.
  • On a cluster (CIT): a test step that goes over its memory and walltime, plus a chunked submission where the failure happens before the children are submitted.

Open questions

  1. Hosting the monitor on Alliance clusters. sbatch from inside a job is confirmed, and scrontab is disabled on rorqual, fir and narval. Still to do: repeat the checks on nibi (commands under cluster facts). Ask Alliance support whether a 1-CPU, 24 h, mostly idle monitor job is acceptable, and whether one sacct every 10–30 min is fine.
  2. Thread-dependent tools. Which steps give different output with a different thread count? They get hash_resources = threads by default.
  3. PBS/Abacus. How would a monitor run there? What happens to afterok children when the parent fails under Torque? Does qalter -W depend= work for reconnecting them?
  4. Defaults. Default retry_max_attempts, factors, monitor_interval, and per-cluster caps.
  5. JVM resource flags. Is -Xmx, -Xms, -XX:ParallelGCThreads, -XX:ConcGCThreads, -XX:ActiveProcessorCount the right list? Are there tools where one of them changes the output?

Decisions

  1. Project tracking: one operation per run, not per attempt. A GenPipes run stays a single operation. A job's retries are recorded as attempts of that job inside it (attempt number, failure class, resources, scheduler id), and the job's final state is its last attempt.
  2. java_other_options stays in the hash. Its content depends on the tool, so only known JVM resource flags inside it become tokens. The flag list is still an open question.
  3. Remove daemon from the -j choices. It is a leftover: a DaemonScheduler drafted in 2014 that printed the pipeline as JSON for an external runner. It was dropped from the options in 2015 and the class was deleted in 2024, but the choice stayed in core/pipeline.py, so -j daemon currently fails. Done in phase 0.
